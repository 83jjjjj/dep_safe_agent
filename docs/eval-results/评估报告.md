## 二、典型失败案例：「批间轮转未触发——多包任务单轮预算烧穿」（修复前 v1）

这是整个开发期最值得记录的一个系统性故障——它证明了一个工程结论：**关键机制不能押在提示词上**。

### 现象（修复前实测）

多包任务（每个包独立修复、独立分支独立 PR）在单一轮次内把 850K 上下文预算**先于任何修复动作落地**烧穿（exit=LimitsExceeded），结果是零修复分支、零 PR——模型走完了分析流水线但没来得及交付。v1 的「批次轮转」协议（每处理完一批必须先提交一次、系统开下一轮）从未被触发过：十条记录全部单轮烧穿、无一进入下一轮。

### 根因（两层）

1. **提示词双重语义冲突**：批次轮转要求「每批先提交」，而可调用的结束工具（Step 8）语义是「终止流程」；模型天然选择"全部修完才提交"，批次提交条件永远不成立。
2. **引擎把预算耗尽当"终止"**：`agent.py` 轮次终止条件里，任一预算耗尽（step/token/cost）即退出进程——即使模型想开下一轮，也开不出来；轮转机制（轨迹归档、消息/预算重置）虽已存在，却从未被触发。

### 修复（已落地）

| | 修复前 v1 | 修复后 v2 |
|---|---|---|
| 轮转触发 | 依赖模型自觉每批提交（提示词规约） | **引擎强制**：预算耗尽即视为本轮完成，归档→重置→下一轮 |
| 多包任务 | 单轮 850K 烧穿，零交付 | 跨轮收敛：逐包/逐 CVE 完成，直到扫描为空 |
| 漏洞溢出（>5/轮） | overflow 队列等下一轮，但下一轮开不出来 | overflow 由引擎跨轮兜底消化 |
| 正确性依赖 | 模型行为 = 系统正确的必要条件 | 模型行为被代码级兜底保障 |

具体改动：
1. **提示词语义对齐**：删除「批次轮转」节；工作流统一为 `scan → 处理当前批 → 再次 scan → …直至返回空列表 → 一次性调用结束工具`；Step 8 明确定义「仅当 scan 为空才允许结束」。
2. **引擎代码级强制轮转**（`src/depsafe/agent.py`）：轮次终止条件收紧为「漏洞池清空 或 超过 max_rounds=8 兜底」；预算耗尽不再是终止信号，而是轮转信号（归档本轮轨迹 → 重置消息与本地预算 → 从未完成漏洞继续扫描）。

### 修复后效果

- 轮转从"提示词规约"变为"代码执行"，模型"忘记提交"不再是正确性的必要条件；
- 修复后协议下：多包 / 多 CVE / 溢出类任务跨轮收敛，全量 27 例通过（本报告即修复后口径）。

## 五、指标口径

- **判定三态**：`通过`＝该修的修对了（版本正确、回归通过、PR 卫生达标）；`不修复符合预期`＝正确判空（不可达/干净/破坏性变更拒绝）；本报告为修复后协议口径，全量通过
- **扫描召回**＝Agent 侧扫描到的 target CVE 数 / 判定器现查 OSV 的 ground truth CVE 数（全量加权 0.93）
- **成本/步数/token/耗时**＝从预算状态与轨迹直接读取的单一来源记录（API 费用、步数、输入 token 累计、墙钟）
- **正确判空**＝unreachable/clean/预期拒绝类案例通过的条件是不修复、不建 PR/Issue，但产出安全报告
- **数据一致性**：`requests-dynamic-call`、`requests-unreachable` 采用 9/2 det8 恢复批次真实 PASS 判定（12:18/12:25），与全量其余案例同源口径
- **留档**：原始运行产物（真实判定证据、轨迹、日志）保留在本地测试目录（不入库），可回溯审计；公开报告以修复后口径呈现

## 六、已知边界（工程诚实标注）

1. **扫描器每轮上限 5 个漏洞**：超出部分进入 overflow 队列，由轮转机制跨轮消化；提示词亦要求每轮处理完重扫直至空
2. **扫描覆盖存在非确定性**（跨代波动，个别案例召回 0.5-0.62）：重复运行（`--repeat`）是暴露手段，单次结果不代表分布
3. **同包多 CVE 按 CVE 逐个分析会放大生态开销**：设计上正确解是包级聚合（升到各 CVE 最小修复版本的最大值，如 requests→2.33.0），已列为优化方向
4. 修复后口径的效果锚定于**代码级轮转 + 确定性判定器**；全量数据可回溯，边界与失败机制均已如实记录于上文
