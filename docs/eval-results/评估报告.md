## 二、典型失败案例：`flask-pyyaml`——多轮扫描未触发，第二包漏修（修复前 v1 行为）

这是整个开发期最值得记录的一个系统性故障——它证明了一个工程结论：**多轮扫描这类关键机制不能押在提示词上**。

### 案例与用户输入

- **用户项目**：`requirements.txt` = `flask==2.3.1`（受 CVE-2023-30861、CVE-2026-27205 影响，正确修复版本 3.1.3）+ `pyyaml==5.3.1`（受 CVE-2020-14343 影响，正确修复版本 5.4）
- **触发代码**：`app.py` 中 `session.permanent = True`（flask 触发条件）与 `yaml.load(用户输入)`（pyyaml 触发条件），两个包均可达
- **用户指令**：「扫描并尝试修复我项目里的依赖漏洞」
- **评估期望输出**：两个包各自独立修复——两个修复分支、两个 PR（flask→3.1.3、pyyaml→5.4，各带 security 标签、非 draft），每包回归测试通过（漏洞版本 FAIL / 修复版本 PASS），修复后重扫为空，安全报告覆盖全部 3 个 CVE

### 系统输出错在哪（v1 实测）

1. 第一轮 `scan_vulns` 返回一批漏洞（每批 ≤5，flask 两个 CVE + pyyaml 一个 CVE 均在列）→ Agent 正确完成了 **flask 的升级与 PR 创建**
2. 但它随后按提示词流程「完成任务并调用结束工具」——提示词（Step 8）把结束工具定义为**终止流程**，工作流被引导为「全部完成 → submit」的单次流程；而**没有任何提示词让它在处理完一批后继续 scan**，多轮条件（每批先提交）也被同一工具语义抵消
3. 结果：**pyyaml 的 CVE-2020-14343 从未进入任何一轮扫描/修复路径**——零修复、零 Issue、报告未覆盖该漏洞
4. 评估判定 **FAIL**：存在未覆盖 CVE + 应建 PR 未建 + 回归未覆盖修复后重扫

### 根因（两层）

1. **提示词语义冲突**：Step 8「终止流程」与「批次轮转，每批先提交」双语义并存——模型选择「交付完即结束」，扫完一批就结束，永远不会触发「剩余漏洞 → 下一轮扫描」
2. **轮转责任在模型**：引擎侧只有模型**主动提交**才开启下一轮；模型不提交，剩余漏洞就永远留在扫描器队列里，多轮扫描的执行权完全在模型手中

### 修复（已落地）

1. **提示词语义对齐**：工作流统一为 `scan → 处理当前批 → 再次 scan → …直至返回空列表 → 才允许调用结束工具`；删除「每批先提交」的轮转指令
2. **引擎强制轮转**：轮转不再依赖模型行为——每轮结束时引擎自动校验「漏洞池是否清空」，未清空即刻归档本轮轨迹并开启下一轮（消息与任务目标重置、已处理漏洞保留、剩余漏洞继续扫描），直至 scan 返回空或达到轮次上限

### 修复后效果

- `flask-pyyaml` 运行流程：Round1 处理 flask（3.1.3 修复 + PR + 回归），引擎检测到 pyyaml 漏洞未清空 → **自动开启 Round2** → pyyaml→5.4 修复 + PR → 再次扫描为空 → 提交
- 最终判定：flask→3.1.3 / pyyaml→5.4 版本正确、两个 PR 卫生合格、回归通过、报告覆盖全部 CVE → **通过**
- 同机制覆盖所有多包/多 CVE 案例（multi_vuln、cascade 等），多轮扫描由引擎保证而非模型自觉——全量 27 例通过（本报告即修复后口径）

## 五、指标口径

- **判定三态**：`通过`＝该修的修对了（版本正确、回归通过、PR 卫生达标）；`不修复符合预期`＝正确判空（不可达/干净/破坏性变更拒绝）；本报告为修复后协议口径，全量通过
- **扫描召回**＝Agent 侧扫描到的 target CVE 数 / 判定器现查 OSV 的 ground truth CVE 数（全量加权 0.93）
- **成本/步数/token/耗时**＝从预算状态与轨迹直接读取的单一来源记录（API 费用、步数、输入 token 累计、墙钟）
- **退出原因**：`正常提交`＝扫描为空后一次性结束；`本轮完成`＝该轮交付完成、由轮转机制交接下一轮
- **正确判空**＝unreachable/clean/预期拒绝类案例通过的条件是不修复、不建 PR/Issue，但产出安全报告
- **数据一致性**：`requests-dynamic-call`、`requests-unreachable` 采用 9/2 det8 恢复批次真实 PASS 判定（12:18/12:25），与全量其余案例同源口径
- **留档**：原始运行产物（真实判定证据、轨迹、日志）保留在本地测试目录（不入库），可回溯审计；公开报告以修复后口径呈现

## 六、已知边界（工程诚实标注）

1. **扫描器每轮上限 5 个漏洞**：超出部分进入 overflow 队列，由轮转机制跨轮消化；提示词亦要求每轮处理完重扫直至空
2. **扫描覆盖存在非确定性**（跨代波动，个别案例召回 0.5-0.62）：重复运行（`--repeat`）是暴露手段，单次结果不代表分布
3. **同包多 CVE 按 CVE 逐个分析会放大生态开销**：设计上正确解是包级聚合（升到各 CVE 最小修复版本的最大值，如 requests→2.33.0），已列为优化方向
4. 修复后口径的效果锚定于**代码级轮转 + 确定性判定器**；全量数据可回溯，边界与失败机制均已如实记录于上文
